# Feature Specification: 自主规划客服智能体

**Feature Branch**: `001-autonomous-customer-service-agent`

**Created**: 2026-08-23

**Status**: Draft

**Input**: User description: "我想规划一个能自主规划的智能体，主要应用于客服agent，能面对不同类型，第一步还不知道客户什么需求的场景，并且能处理退货、推荐、查询货物是否有货等等；"

## Clarifications

### Session 2026-08-23

- Q: 当 LLM 向下游程序或 Agent 输出可执行计划时，应优先采用什么格式？ → A: 严格 JSON Schema / Pydantic Structured Output；JSON 作为机器间协议，禁止依赖 Markdown 或自由格式文本解析。
- Q: 整个开发流程是否应按可独立验证、可替换的组件逐步搭建？ → A: 是；每个组件必须有明确输入/输出契约、独立测试和替换边界，再按依赖顺序组合成完整 Agent。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 识别未知需求并规划对话 (Priority: P1)

当客户首次发起咨询、尚未明确说明需求时，客服智能体能够通过简短、自然的追问判断客户意图，并规划完成任务所需的对话步骤。

**Why this priority**: 这是所有客服场景的入口，决定智能体能否在开放式表达下继续服务客户。

**Independent Test**: 使用若干没有明确意图的客户开场白进行测试，确认智能体能在不重复询问、不臆测关键事实的情况下，将客户引导到明确的服务目标。

**Acceptance Scenarios**:

1. **Given** 客户只说“你好，我想咨询一下”，**When** 智能体收到消息，**Then** 智能体以不超过两个核心问题了解客户需要，并提供常见事项选项作为辅助。
2. **Given** 客户表达含糊且存在多种可能意图，**When** 智能体追问后仍无法确定，**Then** 智能体总结已知信息、说明还缺少的信息，并请求客户确认下一步。
3. **Given** 客户意图已明确，**When** 智能体完成意图判断，**Then** 智能体向客户确认理解结果，并进入对应服务流程。

---

### User Story 2 - 查询商品与库存 (Priority: P1)

当客户询问商品信息或是否有货时，客服智能体能够识别商品、规格和数量需求，返回可验证的结果，并在缺货时给出替代路径。

**Why this priority**: 库存查询是高频、明确且适合优先自动化的客服任务，能直接减少人工查询成本。

**Independent Test**: 分别使用明确商品、缺少规格、库存充足、库存不足和无法识别商品的输入进行测试。

**Acceptance Scenarios**:

1. **Given** 商品和规格可唯一匹配且有库存，**When** 客户询问是否有货，**Then** 智能体返回商品、规格、库存状态及结果时间，并提示客户可进行的后续操作。
2. **Given** 客户只提供商品名称但存在多个规格，**When** 智能体查询库存前，**Then** 智能体只追问影响库存判断的必要规格信息。
3. **Given** 商品缺货，**When** 智能体返回查询结果，**Then** 智能体明确说明缺货状态，并在可用时推荐相近规格、替代商品或到货提醒。
4. **Given** 商品无法匹配或库存信息不可用，**When** 智能体处理请求，**Then** 智能体不编造结果，说明原因并提供转人工或留下联系方式的选项。

---

### User Story 3 - 处理退货申请 (Priority: P1)

当客户提出退货诉求时，客服智能体能够确认订单与退货原因，判断是否满足当前退货规则，指导客户完成申请，并在无法自动判断时转交人工。

**Why this priority**: 退货涉及客户权益和业务规则，既是高频场景，也是需要明确边界与审慎决策的核心流程。

**Independent Test**: 使用符合条件、不符合条件、订单不存在、超过期限、商品状态不明和客户要求人工处理的案例独立验证。

**Acceptance Scenarios**:

1. **Given** 客户提供了可识别的订单，**When** 客户提出退货，**Then** 智能体确认订单商品、购买时间和退货原因，并说明后续所需信息。
2. **Given** 订单满足退货条件且资料完整，**When** 客户确认申请，**Then** 智能体创建退货请求并向客户展示申请编号、下一步和预计处理节点。
3. **Given** 订单不满足退货条件，**When** 智能体完成规则判断，**Then** 智能体说明适用原因和可选解决方案，不承诺规则之外的结果。
4. **Given** 退货资格无法由现有信息判断，**When** 智能体发现信息不足或规则冲突，**Then** 智能体暂停自动承诺，收集必要证据并转交人工。

---

### User Story 4 - 提供商品推荐 (Priority: P2)

当客户表达“想买什么”“帮我推荐”等开放式需求时，客服智能体能够通过少量问题理解预算、用途、偏好和约束，给出有理由的候选商品。

**Why this priority**: 推荐可提升转化和服务体验，但依赖更丰富的商品资料，优先级低于客服入口、库存和退货闭环。

**Independent Test**: 使用不同预算、用途、偏好和无明确偏好的客户请求，确认推荐可解释、可购买且不把缺货商品作为首选。

**Acceptance Scenarios**:

1. **Given** 客户提出宽泛的购买需求，**When** 智能体需要补充信息，**Then** 智能体最多优先询问三个最影响推荐结果的问题。
2. **Given** 商品候选满足客户约束且可售，**When** 智能体生成推荐，**Then** 智能体提供不超过三个候选及其适用理由、关键差异和库存状态。
3. **Given** 没有商品完全满足客户条件，**When** 智能体生成推荐，**Then** 智能体明确说明取舍，并允许客户调整预算或偏好后重新推荐。

---

### User Story 5 - 安全兜底与人工接管 (Priority: P1)

当请求超出能力范围、涉及高风险判断、客户明确要求人工，或服务依赖不可用时，客服智能体能够保持上下文并平稳转交人工。

**Why this priority**: 自主规划必须有明确边界，避免错误承诺、错误退货处理或让客户陷入循环对话。

**Independent Test**: 模拟敏感请求、连续三次未理解、外部信息不可用和客户要求人工的情形，确认均能触发可追踪的接管流程。

**Acceptance Scenarios**:

1. **Given** 客户明确要求人工，**When** 智能体收到请求，**Then** 智能体停止重复自助引导，确认转接并保留已收集的上下文。
2. **Given** 智能体连续三轮无法确认客户目标，**When** 对话仍未收敛，**Then** 智能体提供人工服务选项，并向人工展示客户原始诉求和已确认信息。
3. **Given** 关键业务信息暂时不可用，**When** 智能体无法完成查询或操作，**Then** 智能体明确告知当前限制，不展示未经验证的结果，并提供重试或人工处理选项。

### Edge Cases

- 客户在同一轮消息中同时提出库存、推荐和退货等多个诉求；智能体应拆分并确认处理顺序。
- 客户提供的订单号、商品名或规格存在错别字、多个匹配项或相互矛盾；智能体应要求确认，不应自行选择关键对象。
- 客户在流程中改变目标或补充新问题；智能体应保留已完成步骤，并允许切换或返回原流程。
- 客户重复发送消息、长时间不回复或发送空消息；智能体应避免重复执行有副作用的操作，并给出恢复提示。
- 退货操作已提交但客户重复发起申请；智能体应展示已有申请状态，避免创建重复申请。
- 客户要求智能体做超出授权范围的退款、赔偿或规则例外承诺；智能体应转人工。
- 客户输入包含个人敏感信息；智能体只请求完成任务所必需的信息，并避免在回复中暴露不必要的完整信息。

### V2 Multi-Agent Scenarios

V2 在不改变既有 FR-001～FR-018 业务目标的前提下，将单 Agent 执行入口拆分为可替换的 Supervisor、Commerce Agent、After-sales Agent 和 Human Handoff 组件。V2 用户故事使用 `VS-001`～`VS-005` 编号，避免与原有 User Story 编号混淆。

#### VS-001 Supervisor 路由

当客户提出商品咨询、报价、推荐、售后或人工请求时，Supervisor MUST 输出版本化 JSON 路由决策；混合诉求必须支持 `CONTINUE_AGENT`、`SWITCH_AGENT`、`PARALLEL_TASKS`、`ASK_USER` 和 `HANDOFF`，并记录路由原因、置信度和未满足信息。Supervisor 不得调用价格、库存、退款或配置维护工具。

#### VS-002 Commerce Agent

Commerce Agent MUST 复用商品目录、库存、PricingService、RecommendationService、SalesPolicy 和 MembershipPolicy，支持多商品报价、数量修改、报价重算和选中商品库存验证；SKU 只能由 Resolver 产生，业务金额只能由领域服务计算。

#### VS-003 After-sales Agent

After-sales Agent MUST 支持订单问题识别、证据观察、政策评估和受约束解决方案。证据观察不得直接产生退款、换货或赔偿动作；Resolution Ladder 必须输出政策版本、允许等级、推荐等级、确认要求和人工审批要求。

#### VS-004 Commerce Recommendation

推荐必须使用确定性的硬约束过滤、库存过滤和排序服务，最多返回三个候选；LLM 不得生成目录外商品或未经验证的库存状态。

#### VS-005 跨 Agent 接管与恢复

跨域切换或人工接管 MUST 通过版本化 `AgentTask` 传递最小必要的脱敏上下文，并支持任务创建、完成、取消和恢复。恢复 Commerce 任务时不得丢失报价、选中商品、已确认事实或待处理事项。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系统 MUST 接收自然语言客服消息，并识别客户的一个或多个服务意图、关键实体、约束和当前对话状态。
- **FR-002**: 系统 MUST 在意图不明确时提出最少必要的澄清问题，并在达到足够把握前不得执行有副作用的业务操作。
- **FR-003**: 系统 MUST 根据客户目标、已知信息、缺失信息和业务规则生成可解释的服务计划，并支持在执行过程中调整计划。
- **FR-004**: 系统 MUST 支持商品信息和库存查询，至少覆盖商品、规格、可售状态、可售数量或不可用原因。
- **FR-005**: 系统 MUST 在库存结果无法验证、商品无法匹配或信息过期时明确标记不确定性，不得编造库存结果。
- **FR-006**: 系统 MUST 支持退货流程，包括订单识别、原因收集、资格判断、资料补充、申请确认、申请状态反馈和异常转人工。
- **FR-007**: 系统 MUST 在创建退货申请等不可逆或有副作用的操作前获得客户明确确认，并向客户返回可追踪的结果。
- **FR-008**: 系统 MUST 支持基于用途、预算、偏好和约束的商品推荐，并为每个推荐说明主要理由、关键差异和可售状态。
- **FR-009**: 系统 MUST 在推荐前获取影响结果的必要信息，并允许客户修改偏好后重新推荐。
- **FR-010**: 系统 MUST 支持客户随时切换、暂停、恢复或结束当前服务目标，并避免重复执行已经完成的操作。
- **FR-011**: 系统 MUST 在客户要求人工、连续无法理解、业务规则无法判断、关键数据不可用或请求超出授权范围时触发人工接管。
- **FR-012**: 系统 MUST 将客户原始诉求、已确认事实、已执行步骤、待处理事项和失败原因交给人工接管方。
- **FR-013**: 系统 MUST 在每次关键业务操作前后向客户说明将要执行的动作、结果和下一步，使用客户可理解的语言。
- **FR-014**: 系统 MUST 对敏感个人信息采取最小必要收集原则，并在展示或转交时隐藏不必要的敏感字段。
- **FR-015**: 系统 MUST 记录每次意图判断、计划变更、业务操作、客户确认、转人工和异常结果，以便追踪和改进服务质量。
- **FR-016**: 系统 MUST 允许业务人员维护退货规则、商品资料、库存状态、推荐约束和人工接管条件，并使规则变更可追溯。
- **FR-017**: Planner MUST 向下游程序或 Agent 输出符合版本化 JSON Schema 的结构化结果，至少包含当前目标、目标状态、单个下一步动作、动作参数、原因代码、缺失信息和确认要求；下游在执行前 MUST 完成结构校验，校验失败时不得执行工具或有副作用操作。
- **FR-018**: 系统 MUST 将会话状态、Planner、动作路由、工具适配、领域服务、数据访问、人工接管、前端交互和评估场景定义为具有明确边界的组件；每个组件 MUST 声明输入、输出、失败行为和独立测试方式，并可在不修改无关组件内部实现的情况下被替换或单独验证。
- **FR-019**: V2 MUST 将 Supervisor、Commerce Agent、After-sales Agent 和 Human Handoff 定义为具有版本化输入输出、失败结果、能力白名单和独立契约测试的可替换组件。
- **FR-020**: V2 Supervisor MUST 对多目标请求输出明确的路由模式、任务集合、冲突处理结果和路由原因，不得以固定的单一目标优先级覆盖其他目标。
- **FR-021**: V2 MUST 通过共享状态和版本化 AgentTask 传递最小必要的脱敏上下文，并为状态字段定义类型、生命周期、写入权限和版本冲突处理方式。
- **FR-022**: V2 After-sales MUST 将证据观察、政策判断和副作用执行分离；退款、换货、赔偿等动作必须经过政策、确认、人工审批（若要求）和幂等校验。
- **FR-023**: V2 MUST 为每个 SC-001～SC-009 提供可执行场景、计算公式、阈值和失败样例，并在评估结果中保留对应 SC 编号。
- **FR-024**: V2 多 Agent 路由和任务转换 MUST 写入 Trace，且 Inspector/API 能展示当前 Agent、任务栈、路由原因、证据状态、政策等级和接管历史。

### Key Entities

- **客户会话**：客户、消息、当前目标、已确认事实、待补充信息、计划步骤和服务状态。
- **客户意图**：客户希望完成的任务，如库存查询、退货、推荐或其他待识别事项，以及识别置信度和澄清记录。
- **服务计划**：为达成客户目标而安排的步骤、依赖、所需信息、执行状态和可回退动作。
- **商品**：商品名称、规格、属性、价格、可售状态和替代关系。
- **库存记录**：商品与规格对应的可售数量、查询时间、来源状态和不可用原因。
- **订单**：订单标识、客户、商品、购买时间、履约状态和关联退货申请。
- **退货申请**：退货原因、资格判断、所需材料、客户确认、处理状态、申请编号和人工处理记录。
- **推荐结果**：客户偏好、候选商品、推荐理由、取舍说明和可售状态。
- **人工接管记录**：接管原因、会话上下文、转交时间、处理人和后续结果。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 在标准测试集上，至少 90% 的开放式首句能在三轮对话内收敛到明确服务目标或触发人工接管。
- **SC-002**: 对可验证的库存查询，至少 95% 的回复包含匹配商品、规格和结果时间；信息不可用时 100% 明确标注不可用或转人工。
- **SC-003**: 对资料完整且规则明确的退货请求，至少 90% 能在五分钟内完成资格说明和客户确认；不满足条件的请求不得被错误提交。
- **SC-004**: 推荐场景中至少 85% 的首轮推荐符合客户已确认的硬性约束，且首选商品的可售状态可验证。
- **SC-005**: 至少 95% 的人工接管记录包含客户原始诉求、已确认信息、已执行步骤和接管原因，使人工无需让客户重复完整描述。
- **SC-006**: 在客户体验评估中，至少 85% 的客户认为回复清晰、下一步明确；因重复提问或无效循环产生的会话不超过全部会话的 5%。
- **SC-007**: 所有有副作用的业务操作均能追溯到客户确认、操作结果和对应会话；抽样审计通过率达到 100%。
- **SC-008**: Planner 输出的结构化结果在自动化合约测试中的 Schema 校验通过率达到 100%；任何格式或字段校验失败均不会触发工具执行。
- **SC-009**: 首版所有核心组件均能通过独立测试后再组合运行；替换任一模拟业务组件时，未变化组件的测试无需修改，组件契约测试通过率达到 100%。

### Success-Criteria Evaluation Mapping

评估器必须按以下映射生成结果；每个场景记录 `criterion_id`、输入、预期、实际、通过状态和失败原因：

| Criterion | Executable evaluation | Threshold |
|---|---|---|
| SC-001 | `open_intent_convergence` | 三轮内目标收敛或接管 ≥90% |
| SC-002 | `inventory_response_accuracy` | 商品/规格/时间 ≥95%；不可用标记 100% |
| SC-003 | `return_confirmation_flow` | 五分钟内完成说明和确认 ≥90%；错误提交 0 |
| SC-004 | `recommendation_constraint_accuracy` | 硬约束满足 ≥85%；首选库存可验证 100% |
| SC-005 | `handoff_context_completeness` | 必要上下文完整 ≥95% |
| SC-006 | `response_clarity_and_loop_rate` | 清晰度代理评分 ≥85%；循环 ≤5% |
| SC-007 | `side_effect_auditability` | 确认、结果、会话可追溯 100% |
| SC-008 | `structured_output_safety` | Schema 通过 100%；非法输出执行副作用 0 |
| SC-009 | `replaceable_component_matrix` | 契约测试通过 100%；替换后无关测试无需修改 |

## Assumptions

- v1 面向已登录或能够提供基本身份/订单信息的客户；匿名客户可进行一般咨询和商品推荐，但涉及订单的操作需要额外验证。
- 库存、商品、订单和退货规则由现有业务数据源提供；本功能规格不规定其内部实现方式。
- v1 优先支持中文文本对话；语音、图片识别和多语言服务不纳入首版范围。
- 推荐结果仅作为辅助决策，不代替客户确认；商品价格、库存和规则以查询时的有效信息为准。
- 涉及退款金额、例外赔偿、疑似欺诈、法律争议或身份风险的请求默认转人工。
- 系统可通过现有客服渠道接收和回复消息，并具备可用的人工客服接管能力。
- v1 默认服务目标是先解决一个主要诉求；V2 支持多个目标并行建模，由 Supervisor 输出任务依赖和阻塞关系，不得静默丢弃目标。
- 开发流程采用组件增量交付：先完成并验证基础契约和状态组件，再逐步接入 Planner、工具、领域服务、API、前端和评估组件；不要求一次性完成整个 Agent。
