# Feature Specification: 主动问题生成（PQG）

**Feature Branch**: `003-proactive-question-generation`

**Created**: 2026-09-01

**Status**: Draft

**Input**: 在 Agent 回复顾客问答之后，主动生成最多 3 个可能的后续问题，支持历史对话检索和 LLM 生成，并通过结构化 JSON 解析展示，以促进销售。

## User Scenarios & Testing

### User Story 1 - 回复后展示后续问题（Priority: P1）

顾客得到客服回复后，可以看到与当前对话相关的最多 3 个后续问题，减少继续提问成本并自然引导购买决策。

**Why this priority**: 这是 PQG 的核心用户价值和最小可用闭环。

**Independent Test**: 使用一段已完成的顾客问答，验证回复后出现不超过 3 个可读、相关的问题；无候选时页面仍正常展示原回复。

**Acceptance Scenarios**:

1. **Given** 顾客问题已被 Agent 成功回答，**When** 回复完成，**Then** 系统异步展示 0 至 3 个后续问题，且不阻塞原回复。
2. **Given** 展示了后续问题，**When** 顾客点击其中一个，**Then** 问题被填入输入框但不会自动发送，顾客可编辑并明确发送。
3. **Given** 候选问题为空或不可用，**When** 回复完成，**Then** 不展示空白占位或错误信息，原对话仍可继续。

### User Story 2 - 基于历史对话检索（Priority: P1）

系统从历史对话中找到与当前上下文相似的后续问句，依据相似度、业务场景和历史频次形成数据驱动的候选。

**Why this priority**: 历史真实问句能提升表达自然度，并为 LLM 生成提供可验证的业务先验。

**Independent Test**: 提供带有已知后续问句的历史对话样本，验证相似上下文能召回候选、按规则排序并去重。

**Acceptance Scenarios**:

1. **Given** 历史库存在相似上下文，**When** 触发 PQG，**Then** 系统召回相关后续问句并记录其来源为历史检索。
2. **Given** 历史库没有足够相似内容，**When** 触发 PQG，**Then** 检索结果可为空，并继续尝试其他可用生成路径。
3. **Given** 多条历史记录表达相同意图，**When** 合并候选，**Then** 只保留去重后的自然表达，并保留频次或相似度依据供排序使用。

### User Story 3 - 基于 LLM 生成候选（Priority: P1）

系统将当前对话历史、最后一轮问答和允许的销售目标注入生成指令，请 LLM 推测最多 3 个顾客可能继续追问的问题。

**Why this priority**: LLM 能覆盖历史库未出现的新场景，是 PQG 的主要泛化能力来源。

**Independent Test**: 使用可控的 LLM 返回值验证提示输入、JSON 解析、字段校验、候选数量限制和异常回退。

**Acceptance Scenarios**:

1. **Given** LLM 返回符合约定结构的 JSON，**When** 系统解析结果，**Then** 仅展示通过内容、安全和相关性校验的候选。
2. **Given** LLM 返回非 JSON、字段缺失、超量或不合法内容，**When** 系统处理结果，**Then** 丢弃无效项并使用检索候选或空结果，不向顾客展示原始错误。
3. **Given** LLM 超时、不可用或服务异常，**When** 触发 PQG，**Then** 原客服回复成功返回，PQG 降级为检索结果或不展示建议。

### User Story 4 - 安全的销售引导（Priority: P1）

系统能够促进顾客了解规格、价格、库存、配送和购买流程，但不会代替顾客做出未经确认的操作或编造商品事实。

**Why this priority**: 主动引导不能损害信任，也不能绕过现有的确认和副作用控制。

**Independent Test**: 使用高风险、转人工、缺货、信息冲突和敏感信息样本，验证候选被过滤或 PQG 被抑制。

**Acceptance Scenarios**:

1. **Given** 对话处于转人工、投诉、高风险或待澄清状态，**When** 回复完成，**Then** PQG 被抑制或只展示必要的澄清问题。
2. **Given** 候选包含未确认的价格、库存、时效、优惠或承诺，**When** 安全校验，**Then** 候选不展示，且不得虚构事实。
3. **Given** 候选涉及个人敏感信息、诱导性话术或与当前问题无关内容，**When** 安全校验，**Then** 候选被过滤。

## Edge Cases

- 当前顾客已明确表示“不需要”“停止推荐”或要求转人工时，不继续主动销售提问。
- 当前回复包含多个商品或意图时，候选必须指向明确上下文，不能混淆商品。
- 检索和 LLM 同时返回重复、冲突或低置信度候选时，去重、排序并过滤冲突项。
- 对话过短、过长、包含乱码或上下文不完整时，允许返回空结果，不影响客服回复。
- 候选引用的商品、规格或活动在当前可用数据中不存在时，不得展示事实性表述。
- 顾客点击建议后修改文本，系统应以顾客最终输入为准并保留正常发送流程。

## Requirements

### Functional Requirements

- **FR-001**: 系统 MUST 在 Agent 成功回复后触发 PQG，并与原回复解耦；PQG 失败不得使原回复失败。
- **FR-002**: 系统 MUST 为每次 PQG 请求使用当前会话历史、最后一轮问答和可用业务上下文。
- **FR-003**: 系统 MUST 支持从历史对话库召回相似上下文中的后续问句，并结合相关性与历史频次排序。
- **FR-004**: 系统 MUST 支持通过可配置的生成指令让 LLM 生成最多 3 个相关后续问题。
- **FR-005**: LLM 输出 MUST 使用版本化 JSON 结构，包含候选问题文本及来源、相关性或置信度等必要元数据；系统 MUST 先校验结构再展示。
- **FR-006**: 系统 MUST 合并检索和生成候选，去重、限制为最多 3 个，并过滤与当前问题重复或明显无关的候选。
- **FR-007**: 系统 MUST 允许候选来源标记为历史检索、LLM 生成或混合来源，并为每个候选保留可追溯依据。
- **FR-008**: 系统 MUST 在 LLM 异常、无相似历史或解析失败时提供检索降级或空结果，并保持原回复可见。
- **FR-009**: 系统 MUST 将点击候选填入输入框，且 MUST NOT 自动发送、创建订单、提交支付或执行其他外部副作用。
- **FR-010**: 系统 MUST 在转人工、投诉、高风险、用户拒绝推荐或关键事实待澄清时按策略抑制 PQG。
- **FR-011**: 系统 MUST 阻止候选编造或未经确认地陈述价格、库存、优惠、配送、商品属性和购买承诺。
- **FR-012**: 系统 MUST 过滤敏感信息、攻击性或胁迫性销售话术，并对输入上下文和输出候选执行必要的脱敏。
- **FR-013**: 系统 MUST 记录 PQG 的触发、候选来源、过滤/降级原因和顾客交互结果，日志不得包含不必要的敏感原文。
- **FR-014**: 系统 SHOULD 支持配置销售目标、允许的引导主题、语言风格、候选数量和抑制策略，而不改变安全底线。
- **FR-015**: 系统 MUST 提供可观察的状态，区分成功、有候选、无候选、抑制和降级，且不得把内部错误直接展示给顾客。

### Key Entities

- **PQG 请求**：一次候选生成任务，包含会话、当前回复、上下文摘要、触发原因和策略版本。
- **问题候选**：展示给顾客的后续问句，包含文本、来源、相关性/置信度、排序和校验状态。
- **检索证据**：支持候选的历史上下文、后续问句频次和相似度等可追溯信息。
- **生成输出**：LLM 返回的版本化 JSON、解析状态、模型信息和失败/降级原因。
- **建议策略**：候选数量、允许主题、销售目标、抑制条件和安全规则的有效配置。
- **交互事件**：候选展示、点击、编辑、发送或忽略等事件，关联会话但遵循隐私最小化原则。

## Success Criteria

### Measurable Outcomes

- **SC-001**: 在正常对话中，至少 95% 的 PQG 响应在原客服回复完成后 3 秒内进入可展示状态；PQG 不使原回复等待。
- **SC-002**: 每次展示的候选数量为 0 至 3 个，100% 通过 JSON 结构和安全校验。
- **SC-003**: 离线评测中，检索候选与当前上下文的人工相关性通过率达到 85% 以上，生成候选达到 80% 以上。
- **SC-004**: 100% 的候选点击仅填入输入框，不会自动发送或触发订单、支付等副作用。
- **SC-005**: 在高风险、转人工、明确拒绝推荐和未确认关键事实场景中，PQG 抑制准确率达到 100%。
- **SC-006**: LLM 不可用或返回非法 JSON 时，100% 的原客服回复仍可正常完成，并能看到明确的内部降级状态。
- **SC-007**: 通过日志可追溯每个展示候选的来源、校验结果和交互结果，且不记录不必要的敏感内容。

## Assumptions

- v1 面向中文文本客服场景，沿用现有会话、商品知识和客服回复能力。
- 历史对话库为经授权、脱敏后的本地或模拟数据；不要求本特性直接接入真实外部业务系统。
- LLM 通过现有模型适配能力调用，可兼容 Kimi、智谱或其他兼容提供方；具体模型选择属于部署配置。
- PQG 为可选增强能力；顾客始终可以忽略建议并正常自由输入。
- v1 不自动发送建议、不自动下单、不自动支付，也不改变现有人工确认流程。
- 生成提示词、候选 JSON 版本和安全策略需要可审计、可回滚。
