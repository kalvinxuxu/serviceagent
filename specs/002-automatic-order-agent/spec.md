# Feature Specification: 自动接单订单智能体

**Feature Branch**: `002-automatic-order-agent`

**Created**: 2026-08-31

**Status**: Draft

**Input**: User description: "新建自动接单订单智能体"

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 识别订单邮件并提取订单 (Priority: P1)

作为销售或客服人员，我希望系统识别收到的客户订单邮件，将客户、商品、规格、数量、期望交付时间和地址等信息整理成可核对的订单草稿。

**Why this priority**: 准确理解订单是自动接单闭环的入口，能减少人工阅读和录入工作。

**Independent Test**: 使用包含单商品、多商品、自然语言数量和交付要求的模拟邮件，验证提取结果可核对，缺失字段被明确标记。

**Acceptance Scenarios**:

1. **Given** 邮件包含客户身份、商品名称和数量，**When** 系统处理邮件，**Then** 生成结构化订单草稿并保留原邮件关联。
2. **Given** 邮件包含多个商品或规格，**When** 系统处理邮件，**Then** 每个商品作为独立订单项输出，不合并或遗漏数量。
3. **Given** 商品、数量、交付时间或地址无法确定，**When** 系统处理邮件，**Then** 标记缺失或歧义字段，并生成针对性澄清问题，不创建可发送确认。

---

### User Story 2 - 核验商品、价格和库存 (Priority: P1)

作为销售或客服人员，我希望系统对订单草稿中的商品进行匹配并查询模拟库存，准确区分可满足、部分满足、缺货和无法核验的订单项。

**Why this priority**: 库存核验决定回复能否做出可靠承诺，是接单风险控制的核心。

**Independent Test**: 使用商品唯一匹配、多个规格、库存充足、库存不足、缺货和数据不可用的案例，验证每种状态及其原因。

**Acceptance Scenarios**:

1. **Given** 商品和规格唯一匹配且库存足够，**When** 系统核验订单，**Then** 输出可满足状态、可供数量、适用价格和查询时间。
2. **Given** 某订单项库存不足，**When** 系统核验订单，**Then** 输出请求数量、可供数量和缺口，不将订单标记为完全可满足。
3. **Given** 商品无法唯一匹配或库存服务不可用，**When** 系统核验订单，**Then** 输出待确认或不可用状态，不猜测商品、库存或价格。

---

### User Story 3 - 生成客户回复草稿 (Priority: P1)

作为销售或客服人员，我希望系统依据核验结果生成礼貌、清晰的客户回复草稿，说明可供商品、缺口、替代方案和需要客户补充的信息。

**Why this priority**: 草稿能直接降低回复时间，同时把最终对外承诺保留在人工控制下。

**Independent Test**: 对全量满足、部分满足、无法核验和信息缺失四类订单，检查草稿是否与结构化结果一致且不包含未经验证的承诺。

**Acceptance Scenarios**:

1. **Given** 所有订单项均可满足且交付信息完整，**When** 系统生成草稿，**Then** 草稿列出商品、数量、价格、交付信息和下一步确认请求。
2. **Given** 订单仅部分可满足，**When** 系统生成草稿，**Then** 草稿分别说明可满足项、缺口及可选替代或分批交付方案。
3. **Given** 订单信息不完整或核验失败，**When** 系统生成草稿，**Then** 草稿只请求必要补充信息或建议人工处理，不承诺库存、价格或交期。

---

### User Story 4 - 人工确认后发送并追踪 (Priority: P1)

作为销售或客服人员，我希望在发送前查看订单摘要和邮件草稿，确认后发送；系统应记录确认、发送结果和异常，避免重复发送。

**Why this priority**: 对外订单承诺和邮件发送属于副作用，人工确认是 V1 的安全边界。

**Independent Test**: 验证未确认不能发送、确认后只发送一次、重复操作返回已有结果、发送失败可重试且不会伪造成功。

**Acceptance Scenarios**:

1. **Given** 草稿尚未人工确认，**When** 任何组件尝试发送，**Then** 系统拒绝发送并显示待确认状态。
2. **Given** 人工确认草稿，**When** 系统执行发送，**Then** 记录发送时间、收件人、草稿版本和结果标识。
3. **Given** 发送失败或结果未知，**When** 系统返回结果，**Then** 明确标记失败或未知，不显示为已发送，并提供安全重试或人工处理选项。

### Edge Cases

- 同一邮件重复到达时，系统应识别重复来源，避免重复创建订单或发送回复。
- 一封邮件同时包含咨询、订单和售后诉求时，系统应拆分任务并提示处理顺序。
- 商品名称存在别名、错别字或多个匹配项时，系统必须请求确认。
- 数量、单位、币种、交付日期或地址相互矛盾时，系统不得自行选择。
- 客户要求超出库存、价格或交期数据支持的承诺时，草稿必须明确限制。
- 客户邮件包含个人敏感信息时，展示和转交内容应最小化并隐藏不必要字段。
- 人工修改订单项或草稿后，系统应重新核验受影响字段并提升版本号。
- 库存查询过期、部分商品查询成功或服务超时时，结果必须逐项标记状态。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系统 MUST 接收并保存模拟客户订单邮件的来源标识、发件人、主题、正文、附件引用和接收时间。
- **FR-002**: 系统 MUST 判断邮件是否包含订单意图，并将非订单邮件转为待分类或人工处理，不得强行创建订单。
- **FR-003**: 系统 MUST 从订单邮件中提取客户、订单项、商品、规格、数量、单位、期望交付时间、地址、币种和备注，并为每个字段保留来源或置信状态。
- **FR-004**: 系统 MUST 对缺失、冲突、低置信或无法唯一匹配的关键信息生成最少必要的澄清问题。
- **FR-005**: 系统 MUST 将订单项匹配到模拟商品目录；无法唯一匹配时 MUST 停止自动承诺并要求确认。
- **FR-006**: 系统 MUST 查询并返回每个订单项的库存状态、请求数量、可供数量、价格、查询时间和不可用原因。
- **FR-007**: 系统 MUST 区分 `可满足`、`部分满足`、`缺货`、`待确认` 和 `不可用` 状态，不得以部分结果推断整体可满足。
- **FR-008**: 系统 MUST 根据结构化核验结果生成客户回复草稿，草稿 MUST 与商品、数量、价格、库存和交付事实一致。
- **FR-009**: 系统 MUST 禁止草稿自动发送；发送前 MUST 展示订单摘要、核验结果、草稿正文、收件人和版本信息，并获得明确人工确认。
- **FR-010**: 系统 MUST 对确认和发送操作执行幂等控制，重复确认或发送请求不得产生重复订单或重复邮件。
- **FR-011**: 系统 MUST 记录邮件处理、字段提取、商品匹配、库存查询、草稿生成、人工修改、确认、发送和异常等事件。
- **FR-012**: 系统 MUST 在模拟邮箱、商品目录、库存或价格数据不可用时返回可追踪失败状态，不得编造结果。
- **FR-013**: 系统 MUST 支持人工修改订单草稿；修改商品、数量或交付信息后 MUST 重新执行受影响的核验并标记旧结果失效。
- **FR-014**: 系统 MUST 对展示、日志和人工转交内容采用最小必要信息原则，隐藏不必要的个人敏感信息。
- **FR-015**: V1 MUST 仅使用模拟邮箱和模拟商城数据，不得调用真实邮箱发送、ERP、WMS、支付或物流系统。
- **FR-016**: Planner、订单解析、目录匹配、库存查询、草稿生成、确认发送和审计组件 MUST 具有版本化输入输出契约、明确失败结果和独立测试边界。

### Key Entities *(include if feature involves data)*

- **订单邮件**：模拟邮件的来源标识、发件人、主题、正文、附件引用、接收时间和处理状态。
- **订单草稿**：从邮件提取并可被人工修改的客户、订单项、交付信息、缺失字段和版本。
- **订单项**：原始商品描述、匹配商品、规格、请求数量、单位、价格和核验状态。
- **库存核验结果**：订单项对应的可供数量、满足状态、查询时间、数据来源状态和原因。
- **回复草稿**：收件人、主题、正文、事实摘要、草稿版本、确认状态和发送状态。
- **确认与发送记录**：确认人、确认时间、确认版本、幂等标识、发送结果和异常信息。
- **处理追踪记录**：每个解析、匹配、查询、改动、确认、发送和失败步骤的可审计事件。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 在固定模拟订单集上，至少 95% 的明确商品和数量被正确提取；多商品邮件的订单项遗漏率低于 2%。
- **SC-002**: 在库存数据可用的测试场景中，至少 98% 的订单项状态与模拟库存事实一致；数据不可用场景 100% 标记为不可用或转人工。
- **SC-003**: 对信息完整且可核验的订单，系统在 10 秒内生成可供人工审阅的回复草稿，成功率至少 95%。
- **SC-004**: 100% 的对外发送都具备人工确认、确认版本和可追踪发送结果；未确认草稿发送成功数为 0。
- **SC-005**: 重复邮件或重复发送请求在 100% 的测试场景中不会产生重复订单或重复邮件。
- **SC-006**: 试用人员能够在 2 分钟内完成“查看订单 → 核验库存 → 修改草稿（如需）→ 确认发送”的主流程，完成率至少 90%。

## Assumptions

- V1 的邮件来源、商品目录、库存、价格和发送动作均由模拟数据或本地演示服务提供。
- 仅支持中文纯文本订单邮件；附件解析、图片 OCR 和多语言处理作为后续扩展。
- 人工确认由已登录的销售或客服操作员完成，V1 不新增复杂的组织权限模型。
- 订单承诺以核验时的模拟库存、价格和交付规则为准；任何不确定事实都需要澄清或人工接管。
- 当前项目已有通用客服 Agent 的会话、规划、工具契约和追踪模式，本特性复用其边界但保持订单邮件流程可独立验证。
- 移动端、真实邮箱 OAuth、真实订单落库、支付和物流履约不在本特性范围内。
